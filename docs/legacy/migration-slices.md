## First slice: OTA rollout

**Start with `ota_rollout`.** Three jobs tie on one calculation input. OTA has the cheapest parity surface among those three: a latest-row window, a fixed pivot and guarded rounded rates, with an unpartitioned output. Battery adds a calendar range window, a separate row lag, `max_by` and date partitioning. Charging adds timestamp parsing and casts, by-sequence extrema, rounded intermediates and date partitioning. Diagnostics adds the fleet-state join and denominator. OTA also fits the team's requested priority. [OTA spec](jobs/ota_rollout.md) · [Battery spec](jobs/battery_health_daily.md) · [Charging spec](jobs/charging_sessions.md) · [Diagnostics spec](jobs/diagnostic_alerts.md)

The code slice proves one path from an existing input through the job, Rust Delta output, live parity and the Fleet reader. The CLI requires an existing `vehicle_state_rust` table to open. Its rows are irrelevant to OTA. The demo loader seeds both stream inputs in a common directory. In Kubernetes the two streams write to separate PVCs, so a future batch workload would need access to both input paths and a writable analytics path. The existing manifests deploy the streams. ## End-to-end acceptance for slice 1

1. Start with the same logical input on both sides. In a disposable checkout, `python scripts/load_demo_data.py` seeds both stream Delta tables and the expected Spark analytics Delta tables from the committed fixtures. It replaces existing demo outputs and clears reports. For a live-data check, wait for both ingestion paths to cover the same Kafka slice and submit `telemetry.analytics.OtaRollout` against the Spark input. [scripts/load_demo_data.py](../../scripts/load_demo_data.py) · [README.md · Spark batch command](../../README.md#batch-analytics-jobs) · [OtaRollout.scala](../../spark_jobs/analytics/src/main/scala/telemetry/analytics/OtaRollout.scala)
2. Run the OTA fixture parity test with `cargo test analytics::ota_rollout::tests::matches_spark_output` from `rust_pipeline`. Run the Rust binary with `--config config/app_config.yaml analytics ota_rollout`, then `--config config/app_config.yaml validate --job ota_rollout` from the repository root. Confirm that the Rust Delta path and unpartitioned schema match the contract, and that the report passes. In Fleet, select Rust and check the OTA tab reads the suffixed output. [ota_rollout.rs](../../rust_pipeline/src/analytics/ota_rollout.rs) · [parity.rs](../../rust_pipeline/src/analytics/parity.rs) · [mod.rs](../../rust_pipeline/src/analytics/mod.rs) · [main.rs · CLI](../../rust_pipeline/src/main.rs#L77-L95) · [rust_pipeline/src/validate.rs](../../rust_pipeline/src/validate.rs) · [dashboard/app.py · OTA consumer](../../dashboard/app.py#L714-L761)
3. Before switching any scheduled or external reader, compare matched snapshots and check uniqueness at the actual output grain. The live validator joins on the registered keys and checks schema types, null-safe key coverage and values. The battery and charging registrations use fewer key columns than their Spark groupings, so check their narrower key assumptions before using their reports for cutover.
